# constitution-create

## 목적

이 저장소는 문서를 다음 순서로 만든다: `README.md`(있다면) → `docs/constitution.md` → `docs/specification.md` → `docs/plan.md` → `docs/phaseN-todo.md`. 이 skill은 그 중 `docs/constitution.md` 작성을 담당한다 — 이후 모든 문서(specification, plan, phase-todo)가 참조할 **목적 / 성공 기준 / 제약사항**을 명확히 하는 것이 이 문서의 역할이다.

## 정보를 얻는 방식

이 문서의 내용은 다음 세 가지 경로 중 아무 조합으로나 얻을 수 있다. README 유무에 의존하지 않는다.

1. **README.md** — 있으면 참고 자료로 읽는다. 없어도 상관없이 진행한다.
2. **지금까지의 대화** — 사용자가 이미 대화 중에 목적/제약사항/성공 기준을 언급했다면, 다시 묻지 말고 그 내용을 그대로 반영한다.
3. **양방향 질의응답** — 위 두 경로로 채워지지 않는 항목은 다음 두 방식을 상황에 맞게 섞어 쓴다.
   - 사용자에게 직접 질문한다 ("성공 기준이 뭔가요?").
   - 반대로 이쪽에서 먼저 초안(예: 목적 문장, 흔한 제약사항 후보)을 제안하고 사용자에게 맞는지/고칠지 확인받는다. 특히 사용자가 아직 명확히 정리하지 못한 항목일수록, 질문만 반복하기보다 구체적인 제안을 먼저 던져서 대화를 진전시킨다.

## 실행 순서

1. `README.md`가 있으면 읽는다. 없으면 건너뛴다(중단하지 않는다).
2. `docs/constitution.md`가 이미 있으면 내용을 보여주고, 새로 쓸지 / 기존 내용을 기반으로 수정할지 사용자에게 확인한다.
3. 위 "정보를 얻는 방식"에 따라 목적 / 성공 기준 / 제약사항을 채운다. 근거 없이 추측해서 채우지 않는다 — 확실하지 않으면 질문하거나 제안 후 확인받는다.
4. 초안을 사용자에게 보여주고 확인을 받는다.
5. 확인 후 `docs/constitution.md`로 저장한다.
6. 저장 후 다음 단계로 자연스럽게 유도한다 — 아래 "완료 후" 참고.

## 템플릿

이 저장소의 실제 `docs/constitution.md` 구조를 그대로 따른다:

```markdown
# Project Constitution

## 목적

- [프로젝트가 해결하는 문제/제공하는 가치를 한두 줄로]
- [기능 구현 외에 추가로 얻고자 하는 목적이 있다면 — 예: 특정 기술 학습, 인프라 실습 등]

## 성공 기준

- [이 프로젝트가 "성공"했다고 판단할 구체적 기준 1]
- [기준 2 — 필요한 만큼 추가]

## 제약사항

- **[제약 항목명]**: [값/설명]
- [운영 비용, 유지보수 인원, 기한 등 실제로 존재하는 제약만 기록 — 없는 제약을 지어내지 않는다]
```

## 주의사항

- 이 문서는 이후 `specification.md`, `plan.md`가 모두 참조하는 최상위 문서다. 애매하거나 근거 없는 내용을 채우지 말고, 확신이 없으면 반드시 사용자에게 질문하거나 제안 후 확인받는다.
- README나 대화에 없는 내용을 상상해서 채우지 않는다.

## 완료 후

`docs/constitution.md` 저장이 끝나면, 같은 응답에서 바로 다음 단계로 이어갈지 물어본다: "이제 이 constitution을 바탕으로 요구사항 명세(`docs/specification.md`)를 작성할까요?" 사용자가 동의하면 `specification-create` skill로 이어간다. 그냥 "저장했습니다"로 끝내지 않는다 — 다음 단계 제안까지가 이 skill의 완료 조건이다.
