# 인프라 및 외부 통합

## 개요

- **petshop-back** 프로젝트가 연결되는 외부 시스템(저장소·결제·시크릿)의 명세입니다.
- Persistence(저장소) 영역, 결제(Toss Payments) 연동, 미디어 저장(S3), 배포, 환경/시크릿 관리 정책을 다룹니다.
- **인증 없음** — 비회원(게스트) 체크아웃만 지원하므로 별도 Auth 섹션이 없습니다.
- 어댑터 계층의 코드 패턴(Repository 등)은 `.claude/rules/patterns.md`를 참조합니다.

## Persistence (out)

### 데이터 저장소

| 저장소     | 용도                                                            |
|---------|---------------------------------------------------------------|
| MySQL   | 주 RDBMS — 로컬: Docker Compose로 컨테이너 실행 / 운영: AWS RDS           |
| AWS S3  | 상품 이미지 정적 호스팅 — 최초 상품 등록 시 운영자가 1회성으로 수동 업로드(콘솔/CLI), 업로드 API 없음 |

#### 스키마 변경 규칙

- **Flyway 또는 Liquibase 미사용**. 모든 스키마 변경은 대상 DB에 직접 수동 SQL 스크립트를 실행해야 합니다.
- **단,** 사용자의 요청에 의해서만 스키마 생성/변경에 대한 SQL script를 작성합니다.
- 프롬프트에서 직접적으로 DB와 연결하지 않으며, 스키마 구성 파악을 위해서는 `{도메인명}JpaEntity.java`를 확인합니다.

#### 로컬 환경

- MySQL은 **Docker Compose**로 실행합니다 (컨테이너 구성 파일은 별도 작업으로 준비).
- 프로파일: `application-local.yml`.

#### 운영 환경

- **AWS RDS(MySQL)** 사용. `ddl-auto: none`, 수동 마이그레이션 원칙은 로컬과 동일하게 적용됩니다.
- 프로파일: `application-prod.yml`.

## 결제 연동 (Toss Payments)

- 별도 SDK 없이 **Spring RestClient**로 직접 연동합니다.
- 결제 승인(confirm) 시 클라이언트가 전달한 금액과 서버가 계산한 주문 총액을 대조 검증한 뒤 Toss confirm API를 호출합니다.
- Webhook은 `paymentKey` 기준으로 **멱등 처리**해야 합니다(중복 호출에도 동일 결과 보장).

## 미디어 저장 (S3)

- 용도: **상품 이미지**. 운영자가 최초 상품 등록 시 콘솔/CLI로 **1회성 수동 업로드**합니다.
- 관리자 기능이나 유저 업로드 기능이 아니며, 업로드/관리를 위한 API는 만들지 않습니다.
- 이미지 URL은 상품 테이블(DB)에 직접 기록하고, 조회 API는 저장된 URL을 그대로 응답에 포함합니다.
- 접근 방식은 버킷 정책 기반 **public-read**로 가정합니다(운영자가 직접 구성). CDN(CloudFront) 등은 현재 스코프 밖입니다. **단,** 실제 버킷 정책·리전 등 구체 설정은 사용자 확인 후 진행합니다.

## 로깅 및 모니터링

### 애플리케이션 로그 (에러 추적 겸용)

- Spring Boot 기본 **Logback 콘솔(stdout) 출력**을 그대로 사용합니다. 주문/결제 등 비즈니스 이벤트와 예외(`log.error` + 스택트레이스)를 모두 이 표준 로거로 남깁니다.
- 컨테이너 실행 시 `--log-driver=awslogs` 옵션으로 CloudWatch Logs에 전송합니다(별도 로그 수집 에이전트 불필요).
- 로그 확인/검색은 **CloudWatch Logs Insights**를 사용합니다. 예외도 이 로그 안에 함께 남으므로 별도 에러 추적 도구(Sentry 등)는 두지 않습니다.
- `orderId`, `paymentKey` 등 필드 단위로 정확히 필터링해야 하는 시점이 오면 구조화 로깅(JSON, 예: logstash-logback-encoder) 도입을 고려합니다 — 현재는 **미정**, 필요해질 때 별도로 결정합니다.

## 배포 (Deployment)

- 예산 제약: **월 $5 이하**, 유지보수 인원 1명 → 과설계 지양, 단순한 구조 우선.
- 컨테이너 방식으로 진행하며, **1단계**는 AWS **ECR**에 이미지를 push하고 **EC2 단일 인스턴스**(프리티어/최소 사양)에서 Docker로 pull & 실행하는 구성입니다.
  - 이유: ECS/EKS는 ALB 등 부대 비용이 발생해 예산을 바로 초과하기 쉽습니다. EC2 + ECR 조합은 예산 안에서 컨테이너 빌드 → 레지스트리 push → 서버에서 pull/실행이라는 흐름을 익히기에 적합한 시작점입니다.
- 향후 확장 경로로 ECS/EKS 마이그레이션을 목표로 두되, 현재는 **착수하지 않으며 시점·방식 모두 미정**입니다. 실제 전환 시점에 비용/트래픽을 다시 검토해 별도로 결정합니다.
- **CI/CD**: **GitHub Actions**를 사용합니다. 별도 서버(Jenkins 등)를 띄우지 않아도 되어 예산/유지보수 부담이 없고, 빌드 → 컨테이너 이미지 ECR push → EC2 배포로 이어지는 파이프라인을 목표로 합니다.
- EC2 인스턴스 타입, IAM 정책, 파이프라인 구체 설정(워크플로 파일 등)은 이번 문서 범위 밖이며 별도 작업으로 진행합니다.

## 설정 및 시크릿

- DB 자격증명, Toss 시크릿 키 등 민감한 설정은 운영 환경에서 **AWS Secrets Manager**의 **단일 JSON 시크릿**으로 통합 관리합니다(시크릿 개수를 줄여 비용 절감 목적).
- `application-local.yml`, `application-prod.yml`은 **실제 시크릿 값을 포함하지 않고 git에 커밋**합니다. 운영 시크릿은 `spring.config.import=aws-secretsmanager:...` 설정을 통해 런타임에 주입됩니다.
- 설정 및 시크릿과 관련된 모든 정보는 로컬 메모리와 세션에도 저장하지 않습니다. **즉,** 외부 노출이 되어서는 절대 안 됩니다.
- 로컬 개발은 Docker Compose MySQL의 로컬 전용 자격증명만 필요하며 Secrets Manager를 사용하지 않습니다.
- 테스트 프로파일(`application-test.yml`) 전략은 **아직 미정**입니다. (`build.gradle`에 H2 의존성이 있으나 확정된 방침은 아니므로 임의로 단정하지 않습니다.)

```bash
export AWS_PROFILE=<프로필명>
export AWS_REGION=ap-northeast-2
```
